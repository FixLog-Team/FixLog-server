# 문서 이미지 검색 설계

> 상태: 구현 완료 (서버)
> 범위: FixLog 문서의 `image` 블록 전부 / 글자 + 그래프·도표·그림의 의미까지 검색·답변

---

## 1. 전체 흐름

```
① 업로드    POST /api/images/upload
            → 스토리지(OCI) 저장 + 메타데이터 기록 → 즉시 URL 반환
            → 뒤에서 비동기로 Gemini 분석 시작

② 분석      이미지 → "검색용 텍스트" 생성
            [글자] 에러 메시지·로그·축 라벨·수치
            [종류] 스크린샷 / 다이어그램 / 차트 / 표 / 사진
            [의미] 차트면 추세와 수치, 다이어그램이면 구성요소와 관계

③ 저장      PUT /documents/{id} (기존 그대로)
            blocks에서 참조된 이미지에 document_id를 채운다 (커밋 전, 같은 트랜잭션)

④ 색인      기존 임베딩 파이프라인에 올라탐
            본문 청크 + 이미지 분석 청크를 함께 벡터화 (metadata.source로 구분)

⑤ 검색/답변  기존 검색·AI 답변 경로 그대로
            이미지에서 나온 근거는 source=image, imageId로 짚어준다
```

**분석 완료 → 재색인** — ①의 분석이 끝나기 전에 ③ 저장이 일어나면 그 이미지는 색인에서 빠진다.
그대로 두면 다시 저장할 때까지 검색되지 않으므로, 분석이 끝난 시점에 `ImageAnalyzedEvent`로
그 문서의 **이미지 청크만** 다시 넣는다. 본문 청크는 건드리지 않는다.

**비용 통제** — 같은 이미지는 내용 해시(sha-256)로 식별해 한 번만 분석한다. 문서를 여러 번 저장해도,
같은 스크린샷을 여러 문서에 붙여도, 문서를 복제해도 비전 모델 호출은 1회다.
분석 프롬프트는 모든 이미지에 매번 실려 나가는 고정 비용이라 짧게 유지한다 — 작은 이미지는
이미지 자체(약 258토큰)보다 지시문이 더 비싸다. **크기로 이미지를 걸러내지는 않는다.**
잘라낸 에러 메시지나 작은 차트처럼 작아도 핵심인 경우가 있어, 크기는 정보 가치의 척도가 못 된다.

**폭주 처리** — 비전 분석은 임베딩과 **분리된 실행기**에서 돈다. 한 문서에 이미지를 수십 장 넣고
저장하면 분석이 큐를 채워 문서 색인까지 밀리기 때문이다. 거부 정책은 `CallerRunsPolicy`로,
큐가 넘치면 느려질지언정 분석이 사라지지는 않는다. 분석 시작이 실패해도 업로드는 성공하고
이미지는 `PENDING`으로 남는다.

**일일 상한** — 워크스페이스당 하루 **300건**까지만 비전 모델을 부른다. 해시 재사용 건은 세지 않는다.
상한에 걸려도 업로드와 이미지 사용은 막지 않는다. 그 이미지는 `PENDING`으로 남고 다음 날 정비 작업이 다시 집어간다.
비용 때문에 이미지 첨부 자체를 막을 이유는 없기 때문이다.

**고아 이미지** — 삽입했다 지우고 저장하지 않으면 어느 문서도 참조하지 않는 이미지가 남는다.
매일 정비 작업이 참조가 끊긴 이미지를 지운다. 막 올라온 이미지를 지우지 않도록 **24시간 유예**를 둔다.
휴지통에 있는 문서가 쓰는 이미지는 복원될 수 있으므로 남긴다.

## 2. 이미지 저장 — OCI Object Storage (S3 호환)

버킷은 private으로 두고, 조회는 **서버가 스토리지에서 읽어 바이트를 직접 내려준다.**

서명 URL로 리다이렉트하지 않는 이유는 두 가지다.
- 서명 URL은 한 번 나가면 **만료 전까지 권한을 회수할 수 없다.** 공유를 끊어도 그 URL은 계속 열린다
- 스토리지가 다른 origin이라 브라우저가 받으려면 **버킷 CORS 설정**이 필요하다. 서버가 대신 읽으면 전부 같은 origin에 머문다

대가는 서버 대역폭이다. `Cache-Control: private, max-age=300` 과 내용 해시 `ETag`로 재검증이 304로 끝나게 해
반복 전송을 줄인다. 캐시 수명을 짧게 둔 것도 권한 때문이다 — 길면 공유가 끊긴 뒤에도 그만큼 캐시로 보인다.

**접근 권한**

| 이미지 상태 | 볼 수 있는 사람 |
|---|---|
| 문서에 붙어 있음 | 그 문서를 조회할 수 있는 사람. 공유가 끊기면 이미지도 함께 막힌다 |
| 아직 문서에 안 붙음 | 올린 본인만 |

감사 로그는 남기지 않는다. 문서 하나에 이미지가 여러 장이면 열람 한 번에 기록이 장수만큼 쌓여
정작 문서 열람 기록이 묻히기 때문이다.

## 3. 글자 인식 — 별도 OCR 엔진 없이 Gemini 단독

**근거: 검색이 임베딩 유사도라서 글자 한두 개 오차가 결과를 바꾸지 않는다.** `NullPointerException`을
`NullPointerExceptlon`으로 읽어도 벡터는 거의 같은 자리에 찍힌다. 정확 일치 검색이었다면 얘기가 달랐다.

덧붙여 OCR 엔진은 글자만 주고 끝나서 차트 추세나 다이어그램 관계를 알려면 결국 이미지를 LLM에
한 번 더 보내야 한다. 호출이 2회가 되고, 한글 OCR은 무료 엔진 품질이 낮아 유료 API를 써야 한다.

**대신 포기하는 것**: 긴 스택트레이스·커밋 해시·버전 번호처럼 고유 문자열을 정확히 재현하는 것.
생성 모델이라 그럴듯하게 지어낼 수 있다. 프롬프트로 *"못 읽는 글자는 추측하지 말고 생략"* 하게 해
환각 대신 누락을 택하도록 했고, 긴 로그는 전문 복원이 아니라 식별에 필요한 핵심 줄만 뽑게 했다.

**나중에 바꿀 수 있나**: 된다. 원본은 보존되고 분석 텍스트는 다시 만들 수 있는 파생 데이터다.
결과를 `[글자]/[종류]/[의미]` 구획으로 저장해 두어, OCR 엔진을 붙이면 `[글자]`만 교체할 수 있다.

**OCR 엔진이 필요해지는 시점**: 키워드·정확 일치 검색을 추가할 때, 또는 이미지 속 텍스트를
사용자에게 그대로 보여줄 때.

## 4. 알려진 한계

- **복제 문서의 재색인** — `document_id`는 최초로 참조한 문서만 기록한다. 문서를 복제하면 같은 이미지가
  두 문서에 걸리는데, 분석 완료 재색인은 원본 문서만 받는다. 복제본은 다음 저장 때 색인된다.
- **SVG** — 비전 모델이 읽지 못해 분석에서 제외된다(`SKIPPED`). 캡션은 검색된다.
- **백필 없음** — 이번 기능 이전에 올라온 이미지는 분석되지 않는다. 해당 문서를 다시 저장하면
  그때 참조된 이미지가 분석 대상이 된다.
- **고유 문자열 정확도** — §3의 트레이드오프.
