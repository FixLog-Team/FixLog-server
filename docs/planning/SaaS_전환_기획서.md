## 1. 개요

### 1.1 배경

FixLog를 개인 문서 드라이브에서 **학생 대상 협업 SaaS**로 전환한다.

전환의 본질은 **"소유자 검증"에서 "권한 판정"으로의 축 이동**이다.
이 변경은 문서·폴더 도메인 전체에 파급되므로 나머지 모든 설계는 5.1(권한 모델)에 종속된다.

**콘텐츠 계층은 현행 구조를 유지한다** — 폴더 밑에 문서가 생긴다 (D7).

### 1.2 목적

| # | 목적 |
|---|---|
| 1 | 문서·폴더를 개인 소유물이 아닌 **권한으로 통제되는 공유 자산**으로 만든다 |
| 2 | 반출(다운로드)을 열람과 분리 통제하고, 모든 접근에 **책임 소재를 남긴다** |
| 3 | 문서 변경을 되돌릴 수 있게 한다 (리비전 + 롤백) |
| 4 | 워크스페이스 관리자가 구성원·권한·사용 현황·비용을 **직접 운영**할 수 있게 한다 |
| 5 | AI 비용을 서비스가 무한 부담하지 않는 구조로 만든다 |
| 6 | 삭제한 문서를 되찾을 수 있게 하고(휴지통), 라벨로 분류·탐색할 수 있게 한다 |

### 1.3 전환 요약

| 축 | 기존 (개인 드라이브) | 전환 후 (SaaS) |
|---|---|---|
| 소유 단위 | 개인 (`create_user`) | 워크스페이스 > 사용자/그룹 |
| 콘텐츠 계층 | 폴더 트리 + 문서 | **변경 없음** (D7) |
| 접근 제어 | 소유자 본인만 | 권한 기반 (ACL + 상속) |
| 공유 | 없음 | 폴더·문서 공유 |
| 반출 통제 | 없음 | 다운로드 권한 분리 + 워터마크 + 로그 |
| 버전 | 수정 시 덮어쓰기 | 리비전 체인 + 롤백 |
| 삭제 | soft delete (조회 불가) | **휴지통 + 복원** |
| 분류 | 없음 | **라벨** (AI 자동 태그 연계) |
| 운영 | 없음 | 워크스페이스 관리자 콘솔 |
| AI 비용 | 서비스 부담 | 무료 모델 제공 + BYO API Key + 사용량·비용 관리 |

## 2. 결정 로그

> D1~D6 확정 2026-08-04, D7~D8 확정 2026-08-05.
> 변경 시 이 표를 갱신하고 11장 변경 이력에 남긴다.

### D1. 조직(테넌트)의 경계 — 🟢 **자율 생성 워크스페이스**

누구나 워크스페이스를 만들 수 있고, **생성자가 그 워크스페이스의 관리자**가 되어 타 사용자를 초대한다.
학교/학과 같은 외부 조직 구조에 종속되지 않는다.

**근거**: 대상이 학생이고 사용 단위가 스터디·팀 프로젝트다. 외부 조직 등록을 전제하면 서비스가 시작조차 안 된다.

**핵심 귀결**: 한 사용자는 여러 워크스페이스에 속하고 워크스페이스마다 역할이 다르다.

```
User A ─┬─ 개인 워크스페이스   (ADMIN)
        ├─ "OS 스터디"        (MEMBER)
        └─ "졸업프로젝트 팀"   (ADMIN)
```

따라서 **역할은 사용자의 속성이 아니라 (워크스페이스, 사용자) 쌍의 속성**이다.
`UserEntity`에 역할 컬럼을 두면 안 되고 `WorkspaceMemberEntity`로 분리한다.

### D2. 관리자의 관할 범위 — 🟢 **워크스페이스 관리자**

관리자 기능의 주체는 워크스페이스 관리자다. 서비스 전역 운영자 콘솔은 도입하지 않는다.

**귀결**: 관리자 콘솔의 모든 조회는 요청자의 `ADMIN` 멤버십이 있는 워크스페이스로 범위가 한정된다.
**전역(크로스 워크스페이스) 조회 API는 만들지 않는다** — 만들면 그 자체가 권한 우회 경로가 된다.

### D3. 권한 상속 — 🟢 **폴더 상속 + 문서 오버라이드**

폴더에 부여한 권한은 하위 폴더·문서로 상속되며, 문서 레벨에서 개별 오버라이드할 수 있다.

**근거**: 상속이 없으면 "폴더 공유"는 하위 문서를 전부 개별 부여한다는 뜻이 되고,
폴더에 문서를 새로 추가할 때마다 권한이 새는 구멍이 생긴다.

**귀결**: 조상 폴더 집합을 매 요청 재귀 쿼리로 구하면 깊이만큼 DB 왕복이 발생하므로
`FolderEntity`에 **materialized path**를 도입한다 (→ 5.1.4).

### D4. 버전 관리 범위 — 🟢 **리비전 + 롤백**

저장 시점 스냅샷을 남기고 과거 시점으로 되돌린다. **브랜치·머지는 없다.**

**근거**: 브랜치·머지는 블록 JSON의 3-way merge를 요구하며 1차 범위를 벗어난다.

**귀결**: 문서 편집 락은 버전 관리가 아니라 동시 편집 충돌 방지 기능이므로 별건으로 분리한다.
버전 비교(diff) UI도 1차 제외 — 블록 JSON diff는 난도가 높아 2차로 넘긴다.

### D5. AI 사용량·비용 관리 — 🟢 **1차 포함**

무료 모델은 서비스가 제공하고, 고성능 모델은 사용자가 자기 API Key를 등록해 쓴다.
**사용량 집계·한도·비용 리포트까지 1차에 포함한다.**

**영향**: 다음이 함께 필요하다.

- 모델별 요금표와 토큰 단가 관리
- 사용자 API Key 암호화 저장 및 런타임 클라이언트 구성
  (현재 `application.properties:32-60`에 전역 키가 박혀 있어 `AbstractAIService` 계열 재구성 필요)
- 워크스페이스 단위 무료 한도 정의와 초과 시 차단 동작

**권한 모델과 직교하므로 M1 이후 별도 레인으로 병렬 진행 가능하다.**

### D6. 기존 데이터 처리 — 🟢 **실사용 데이터 없음 → 파괴적 재설계**

보존해야 할 실사용 문서가 없으므로 `create_user` 기반 접근 경로를 단계적 마이그레이션 없이 폐기한다.
**Flyway를 도입한다** — 엔티티가 크게 늘어나는데 현재 `ddl-auto=update`
(`application.properties:16`)로는 컬럼 삭제·제약 변경이 반영되지 않는다.

### D7. 콘텐츠 계층 모델 — 🟢 **현행 유지: 폴더 밑에 문서**

폴더가 트리를 이루고, **문서는 폴더 안에 놓인다. 문서는 자식을 갖지 않는다.**

```
[F] 스터디 자료
 ├─ [D] 1주차 정리
 └─ [D] 2주차 정리
[F] 트러블슈팅
 └─ [D] JVM OOM 대응
[D] 임시 메모            ← 루트 문서
```

**근거**: 문서가 문서를 품는 구조로 바꾸면 `FolderService`(290줄)와 `DocumentService`(207줄),
관련 DTO·컨트롤러가 전부 재작성 대상이 된다.
현행 구조를 유지하면 그 비용이 사라지고, 권한 모델(D3)을 얹는 데 필요한 변경만 남는다.

**귀결**:

- 권한 상속은 **폴더 트리를 따라 내려와 문서에 도달**한다
- materialized path는 `FolderEntity`에만 둔다
- 공유는 폴더 공유와 문서 공유 **두 규칙**으로 유지된다
- `/folders/*` API는 그대로 유지된다 — 프론트엔드 계약이 보존된다

**대가**: 문서를 문서 아래에 두는 구성은 불가능하다. 계층을 만들려면 폴더를 써야 한다.

### D8. 추가 기능의 1차 포함 범위 — 🟢 **휴지통 + 라벨**

검토한 후보 7건 중 다음을 1차에 포함한다.

| 기능 | 1차 | 사유 |
|---|---|---|
| **휴지통 / 복원** | 🟢 포함 | soft delete(`usable`)가 이미 있어 비용이 가장 낮고, 권한·감사와 자연히 붙는다 |
| **라벨** | 🟢 포함 | 기존 기획의 태그 개념과 중복이며, 구현된 AI 자동 태그(`/ai/tags`)와 바로 연결된다 |
| 댓글 + @멘션 | 🔴 2차 | — |
| 구독 / 알림 | 🔴 2차 | — |
| 첨부파일 | 🔴 2차 | 스토리지·용량 정책·바이러스 검사가 함께 붙는다 |
| 템플릿 | 🔴 2차 | AI 요약이 유사 역할을 이미 수행한다 |
| 공개 링크 | 🔴 2차 | 익명 접근은 권한·감사·보안 정책 설계를 한 겹 더 요구한다 |

⚠️ **댓글·멘션 제외의 의미**: 1차 산출물은 "권한과 버전이 통제되는 공유 문서함"이며,
**문서 위에서 대화가 오가는 협업 도구는 아니다.** R-07에 리스크로 등록한다.

## 3. 용어 정의

| 용어 | 정의 |
|---|---|
| **Workspace** | 협업·정책·관리자 권한의 경계. 모든 폴더·문서는 정확히 하나의 워크스페이스에 속한다 |
| **Membership** | (워크스페이스, 사용자, 역할)의 결합. 역할은 `ADMIN` \| `MEMBER` |
| **Group** | 워크스페이스 내 사용자 묶음. 권한 부여의 주체. 워크스페이스 경계를 넘지 않는다 |
| **Principal** | 권한을 부여받는 주체. `User` \| `Group` |
| **Resource** | 권한이 걸리는 대상. `Folder` \| `Document` |
| **Permission** | (Principal, Resource, 레벨, 다운로드 허용 여부)의 결합 |
| **Share (공유)** | 별도 개념이 아니라 **권한 레코드를 생성하는 행위** |
| **Revision** | 문서 본문의 시점 스냅샷. 불변 |
| **Label** | 워크스페이스 범위의 분류 태그. 문서에 N:M으로 부여된다 |
| **Trash (휴지통)** | 삭제된 폴더·문서의 보관 상태. 복원 또는 영구 삭제된다 |
| **AuditLog** | 누가·언제·무엇을·어떻게 접근했는지의 append-only 기록 |
| **SecurityPolicy** | 워크스페이스 단위 상위 제약. 개별 권한보다 우선한다 |
| **BYO Key** | Bring Your Own API Key. 사용자가 등록한 고성능 모델 자격증명 |
| **Materialized Path** | 폴더의 조상 경로를 문자열로 비정규화 저장한 컬럼 (`/{rootId}/{aId}/`) |

## 4. 현행 시스템 분석

> 2026-08-04~05, `dev` 브랜치 기준 실측.

### 4.1 소유자 검증이 리포지토리 쿼리에 박혀 있다 🔴

접근 제어가 서비스 레이어의 판정이 아니라 **쿼리 조건**으로 구현되어 있다.

| 위치 | 내용 |
|---|---|
| `DocumentRepository.java:14` | `findByDocumentIdAndCreateUserAndUsable(...)` |
| `DocumentRepository.java:17,20,31,33,42` | 목록·집계 쿼리 전부 `createUser` 결합 |
| `FolderRepository.java:12,14,16,19,28` | 동일 |
| `DocumentService.java:176` | `loadOwned()` — 단건 접근의 유일한 관문 |

**귀결 1**: 남이 공유한 문서는 쿼리 자체가 반환하지 않으므로 **구조적으로 조회 불가능**하다.
공유 기능은 이 쿼리들을 고치지 않는 한 어떤 방식으로도 얹을 수 없다.

**귀결 2**: 권한 조건이 쿼리마다 흩어져 있어 새 쿼리에서 한 번만 누락해도 권한 우회가 된다.
판정은 **단일 지점**으로 모아야 한다.

### 4.2 조직 개념이 없다 🔴

- `UserEntity.java:10-34` — 역할·소속 컬럼 없음
- 그룹·워크스페이스 엔티티 없음
- 소속 표현이 `create_user` 하나뿐 (`DocumentEntity.java:39`, `FolderEntity.java:27`)

### 4.3 권한 거부를 표현할 수단이 없다 🔴

`Code.java:3-9` — `SUCCESS / UNKNOWN / UNAUTHORIZED / NOT_FOUND / INVALID_REQUEST`.
**`FORBIDDEN`이 없다.**

### 4.4 폴더에 조상 경로가 없다 🟠

`FolderEntity.java:15` — `parent_id`만 있고 경로 컬럼이 없다.
D3의 권한 상속을 위해 조상 집합이 필요한데, 현재 구조로는 재귀 조회가 불가피하다 (→ 5.1.4).

### 4.5 삭제된 콘텐츠를 되찾을 경로가 없다 🟠 (D8 대상)

`DocumentEntity.java:98`·`FolderEntity.java:71` — `softDelete()`로 `usable = 0`이 되지만,
**삭제된 항목을 조회하거나 복원하는 API가 없다.** 데이터는 남아 있는데 접근 수단만 없는 상태다.

### 4.6 검색 인덱스가 권한을 모른다 🟠

`DocumentVectorStoreService.java:80` — 청크 메타데이터에 `createUser`만 기록한다.
권한 기반 검색을 하려면 `workspace_id`를 넣고 **검색 시 사전 필터**를 걸어야 한다.
사후 필터링은 상위 N개를 먼저 뽑고 걸러내므로 결과가 비는 문제가 생긴다.

### 4.7 AI 자격증명이 전역 설정에 고정되어 있다 🟠

`application.properties:32-60` — OpenAI / Ollama / Gemini 키가 전역 프로퍼티로 박혀 있다.
D5의 BYO Key를 도입하려면 **런타임에 사용자별 자격증명으로 클라이언트를 구성**하는 구조가 필요하다.

### 4.8 안전망이 얇다 🔴

테스트 총 23건 — `FolderTreeTest` 8, `FolderDocumentReorderTest` 10,
`WorkspaceRemovalFlowVerificationTest` 4, 컨텍스트 로딩 1.
**문서 CRUD·검색·AI·인증에 서비스 레벨 테스트가 없다.**
리포지토리를 재작성하는 작업인데 회귀를 잡아 줄 그물이 없다.

### 4.9 스키마 관리 도구가 없다 🟠

`application.properties:16` — `ddl-auto=update`, Flyway/Liquibase 없음 (→ D6에서 도입 확정).

## 5. 설계

### 5.1 권한 모델 (핵심)

#### 5.1.1 권한 레벨

| 레벨 | 조회 | 편집 | 공유 설정 | 삭제 |
|---|---|---|---|---|
| `OWNER` | O | O | O | O |
| `EDITOR` | O | O | X | X |
| `VIEWER` | O | X | X | X |

#### 5.1.2 다운로드 권한의 분리

**다운로드는 레벨과 독립된 별도 플래그(`can_download`)로 관리한다.**
"열람은 허용하되 반출은 금지"가 DRM 요구의 핵심이므로,
VIEWER/EDITOR 각각에 대해 다운로드 허용 여부를 따로 설정할 수 있어야 한다.

#### 5.1.3 판정

모든 접근은 단일 컴포넌트 `PermissionEvaluator`를 통과한다.
**리포지토리 쿼리에 권한 조건을 넣지 않는다** — 4.1의 실패를 반복하지 않기 위함이다.

| 순서 | 판정 | 실패 시 |
|---|---|---|
| 1 | 리소스가 속한 워크스페이스에 요청자의 멤버십이 있는가 | `NOT_FOUND` |
| 2 | 워크스페이스 정책이 해당 행위를 금지하는가 (5.5) | `FORBIDDEN` |
| 3 | 요청자가 워크스페이스 `ADMIN`인가 | → 허용 (감사 로그에 관리자 접근으로 기록) |
| 4 | 리소스에 직접 부여된 권한이 있는가 (User 우선, 그다음 Group) | → 다음 단계 |
| 5 | 상위 폴더로 거슬러 올라가며 상속 권한 조회 (D3) | → 다음 단계 |
| 6 | 해당 없음 | `FORBIDDEN` |

**1단계에서 `FORBIDDEN`이 아니라 `NOT_FOUND`를 반환한다.**
비멤버에게는 리소스의 존재 사실 자체를 노출하지 않기 위함이다.

**2단계가 3단계보다 앞선다.** 정책은 관리자 권한보다도 상위 제약이다.

#### 5.1.4 상속 조회와 materialized path

상속 조회를 매 요청 재귀 쿼리로 하면 폴더 깊이만큼 DB 왕복이 발생한다.
`FolderEntity`에 `path` 컬럼(`/{rootId}/{aId}/{bId}/`)을 두어 **단일 쿼리로 조상 집합**을 얻는다.
폴더 이동 시 해당 서브트리의 `path`를 일괄 갱신한다.

문서의 조상 집합은 `문서.folder_id → 그 폴더의 path`로 구한다.

#### 5.1.5 워크스페이스 범위 한정

사용자가 여러 워크스페이스에 다중 소속하므로(D1), 모든 목록 조회에
**`workspace_id` 범위 한정이 추가로 필요하다.** 권한이 있어도 현재 컨텍스트 워크스페이스 밖의
리소스는 목록에 섞이지 않는다.

### 5.2 공유

**공유 = 권한 레코드 생성.** 별도의 "공유" 개념을 두지 않고 권한 모델에 흡수시킨다.
"나와 공유된 문서"는 "내가 생성하지 않았지만 권한이 있는 리소스" 조회다.

폴더 공유는 상속을 통해 하위 문서까지 열리고, 문서 공유는 그 문서 하나만 연다.

### 5.3 문서 버전 관리

- 저장할 때마다 리비전을 남긴다. 리비전은 **불변**이며 수정·삭제되지 않는다
- 저장 시 `content_hash`가 직전 리비전과 같으면 리비전을 만들지 않는다
  (`DocumentEntity.java:30`의 기존 해시를 활용한다 — 자동저장이 매초 리비전을 쌓는 것 방지)
- **롤백도 새 리비전을 만든다.** 과거를 지우지 않는다
- 브랜치·머지 없음. 버전 비교(diff)는 2차

### 5.4 휴지통과 라벨 (D8)

#### 5.4.1 휴지통

- 삭제는 기존 `usable = 0` 처리에 삭제자·삭제 시각을 추가로 남긴다
- **폴더 삭제 시 하위 폴더·문서 전체가 함께 휴지통으로 간다.**
  부모만 삭제되고 자식이 트리에 남는 상태를 만들지 않는다
- 휴지통 목록은 워크스페이스 범위이며 권한 판정을 그대로 따른다
- 복원 시 **부모 폴더가 여전히 휴지통에 있으면 루트로 복원**한다 (고아 항목 방지)
- 영구 삭제는 문서·리비전·벡터 청크를 함께 제거한다

#### 5.4.2 라벨

- 라벨은 워크스페이스 범위이며 **문서**에 N:M으로 부여된다
- 부여·제거는 편집 권한 이상을 요구한다
- 라벨로 문서를 필터 조회할 수 있고, 검색 필터로도 쓰인다
- **구현된 AI 자동 태그(`AIController.java:51`)의 결과를 라벨 후보로 제안**한다.
  AI 결과는 항상 제안이며 사용자가 수락해야 라벨이 된다 (CLAUDE.md 원칙)

### 5.5 AI 사용량 및 비용 (D5)

| 계층 | 모델 | 비용 부담 | 통제 |
|---|---|---|---|
| 무료 | 서비스 제공 모델 | 서비스 | 워크스페이스 단위 한도, 초과 시 차단 |
| 고성능 | 사용자 등록 모델 | 사용자 | BYO API Key |

- API Key는 **암호화 저장하고 절대 응답으로 되돌려주지 않는다** (마스킹된 일부만 표시)
- 모든 AI 호출에 대해 요청자·워크스페이스·모델·입출력 토큰·시각·성공 여부를 적재한다
- 비용은 모델별 단가표를 적용해 산정하며, **단가표 변경이 과거 기록을 소급 변조하지 않도록
  집계 시점 단가를 함께 저장한다**

### 5.6 보안 정책

워크스페이스 단위로 관리자가 설정한다.

| 항목 | 기본값 |
|---|---|
| 외부 공유 허용 여부 | 허용 |
| 다운로드 기본 허용 여부 | 허용 |
| 워터마크 강제 여부 | 미강제 |
| 감사 로그 보존 기간 | 1년 |
| 휴지통 보존 기간 | 30일 |

**정책은 권한 판정보다 먼저 적용되는 상위 제약이다** (5.1.3의 2단계).
개별 권한이 다운로드를 허용해도 워크스페이스 정책이 금지하면 금지된다.

### 5.7 DRM의 현실적 한계 ⚠️

다운로드 차단·워터마크로 막을 수 있는 것은 **정상 경로의 반출**뿐이다.
화면 캡처, 사진 촬영, 브라우저에 렌더된 내용의 복사는 서버가 통제할 수 없다.

따라서 DRM 요구를 **"유출 불가능"이 아니라 "유출 시 책임 소재를 남긴다"**로 정의한다.
→ 다운로드 권한 분리 + 전 열람/다운로드 감사 로그 + 워터마크(사용자 식별자 각인).

여기서 막히면 M4 이후는 의미가 없다.

**M2에서 리포지토리를 손볼 때 `create_user` 조건을 새로 넣지 않는다.**
넣었다가 M3에서 걷어내면 같은 코드를 두 번 쓰게 된다.

**병렬 레인**: M2 착수 이후 리비전(M5 일부)과 AI 과금(M6)은 임계경로와 독립적으로 진행할 수 있다.
D5·D8로 마일스톤이 늘었으므로, 이 병렬화를 쓰지 않으면 일정이 그만큼 늘어난다.

**지연 시 잘라낼 순서**: 관리자 콘솔의 **조회** 기능(M8) → 라벨(M7) → 보안 정책 일부(M9).
로그·리비전·사용량 데이터는 계속 쌓이므로 조회 UI를 나중에 붙여도 손실이 없다.

#### 남은 일

| 항목 | 내용 |
|---|---|
| **AI BYO 호출 배선** | 키 보관·복호화까지는 됐고 런타임 클라이언트 구성이 남았다. 현재 모든 호출이 무료 계층으로 간다 (FR-AI-009, 010) |
| **보존 기간 정리 배치** | 정책에 일수는 저장되지만 실제로 지우는 작업이 없다 (FR-AUD-006, FR-TRS-009) |
| **"나와 공유됨"의 폴더** | 문서만 덮었다 (FR-SHR-005) |
| **검색 배선의 실사용 검증** | 필터 SQL과 서비스의 필터 생성은 각각 확인했으나, HTTP 경로에서 둘이 이어지는 것은 미검증 |

#### 설계에서 이탈하거나 추가된 것

| 항목 | 내용 | 이유 |
|---|---|---|
| `PermissionScope` 추가 | 목록 판정용 일괄 적재 경로 | FR-PRM-009(워크스페이스 한정)만 걸면 같은 워크스페이스의 권한 없는 문서가 목록에 노출된다. 판정 규칙 자체는 단건과 같은 코드를 쓴다 |
| 기준 워크스페이스의 출처 | 기존 리소스 연산은 **리소스 자신**의 워크스페이스를 쓴다 (컨텍스트 아님) | 헤더가 가리키는 곳과 리소스가 속한 곳이 다르면 다른 워크스페이스의 형제들과 순번을 겨루게 된다 |
| 목록 페이지네이션 | DB가 아니라 메모리에서 자른다 | 권한 조건을 쿼리에 넣지 않기로 했기 때문. A-03(수백 규모) 가정에 기대고 있으며 M4에서 재검토 |
| 신규 테이블 컨벤션 | snake_case 무따옴표 + uuid PK | 기존 `"fixLog_user"`와 `apj_folder` 두 컨벤션이 충돌해 정한 것 |
| **생성자 소유 권한** | 문서·폴더 생성 시 만든 사람에게 `OWNER` 권한을 부여 | 스펙에 없던 항목. 없으면 일반 구성원이 문서를 만드는 즉시 접근을 잃는다 (M3 결함, M4에서 수정) |
| **휴지통 접근 규칙** | 권한 판정이 아니라 **지운 본인 + 워크스페이스 관리자** | FR-TRS-003은 권한 판정을 따르라고 하지만, 조상 폴더가 함께 삭제돼 경로가 끊긴 상태라 상속 판정이 성립하지 않는다 |
| **"외부 공유 허용"의 재정의** | "구성원 간 공유 허용 여부"로 정의 | 원래 항목은 공개 링크(2차)를 전제해 지금 강제할 지점이 없다. 저장만 하고 안 쓰는 플래그 대신 지금 의미가 있는 제약으로 바꿨다 |
| 감사 로그·사용량의 트랜잭션 분리 | `REQUIRES_NEW`로 별도 트랜잭션 | 거부·실패는 예외로 끝나 본 트랜잭션이 롤백되는데, 같은 트랜잭션에 쓰면 정작 남겨야 할 기록이 함께 사라진다 |

#### M0에서 발견한 기존 결함

계획에 없었으나 안전망을 세우려면 먼저 고쳐야 했던 것들이다.

- `contextLoads()`가 이전부터 실패 중이었다 (자동설정 제외 누락 → 빈 충돌 외 3중 원인)
- `application.properties`가 `GOOGLE_AI_API_KEY`를 읽는데 실제 환경 변수는 `GEMINI_API_KEY`라
  **개발 서버가 기동되지 않는 상태였다**
- `flyway-core`만으로는 Boot 4에서 마이그레이션이 실행되지 않는다 (`spring-boot-flyway` 필요)
